# Module 9 — Practice and assessment

## Exercises

1. Design tenant/product/order/item keys, foreign keys and stock/quantity checks.
   Explain which invariant belongs in storage and which requires authorization.
2. Write a tenant-scoped revenue query including customers with zero orders.
   Explain how a WHERE clause on the joined side can remove those customers.
3. Rank customers by completed-order spend per tenant. Choose tie semantics and
   avoid double-counting when orders also have several audit events.
4. Propose a composite index for recent tenant orders and a partial index for open
   orders. State why the planner might still choose a sequential scan.
5. Describe an EXPLAIN review with badly underestimated outer rows and many inner
   loops. Identify evidence needed before choosing an index/query change.
6. Design an N+1 regression check and compare selectin/joined loading projections.
7. Plan a backwards-compatible column replacement with bounded backfill and
   delayed removal. Include lock/transaction concerns and old application versions.

??? note "Model reasoning"
    Composite relationships can enforce tenant-key consistency, not caller
    permission. Keep aggregation at the intended grain before one-to-many joins.
    Index order follows equality/range/order requirements and data distribution.
    EXPLAIN estimates must be checked against observed rows/loops and buffer work.
    N+1 is visible in actual query count; one huge join can be worse. Expansion,
    backfill, validation and contraction must remain compatible throughout rollout.

## Interview questions

- Why might PostgreSQL ignore an index?
- Does an INCLUDE index guarantee an index-only scan?
- What is the difference between GROUP BY and a window function?
- How can ORM eager loading increase transferred data dramatically?
- Why should an autogenerated migration be reviewed manually?

??? note "Answer guide"
    Small/low-selectivity or mismatched queries can favor scans, while statistics
    may be wrong. Visibility and planner decisions still affect index-only scans.
    Aggregation collapses rows; windows retain them. Collection joins multiply
    rows. Migration tools cannot infer business intent, lock budgets or every
    rename/evolution requirement.

## Mastery assessment

Use 25 for relational/planner concepts, 30 for correct schema/query design, 20
for inflated totals or N+1 diagnosis, 15 for indexing/migration tradeoffs and 10
for communication. Target 80/100. SQL snippets are study answers; no execution
plan measurements are claimed until the deferred database project is run.
